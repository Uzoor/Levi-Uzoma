    New  Case study · Freight · AI extraction

    AI Freight Lead-to-Quote

    Checks a freight inbox every minute and turns each enquiry into a CRM deal, a reply asking for the missing shipment details, and an alert to the owner.

    • n8n
    • Gmail
    • Groq LLM
    • HubSpot

    What happens to each email

    1. Inbox checkGmail is polled every minute for unread mail.
    2. Clean and filterSender name and address are pulled out. No-reply, mailer-daemon and newsletter senders are dropped.
    3. Read the enquiryA language model returns cargo type, origin, destination, container size, urgency and a one-line summary as JSON.
    4. Parse, with a safety netCode fences and stray text are stripped. If the output still cannot be read, the lead is kept and marked for manual review.
    5. Is it an enquiry?Only requests for a quote, shipping, clearing or logistics continue.the flow stops here
    6. CRM recordThe contact is created or updated in HubSpot and a deal opens with cargo, route and container size filled in. Calls retry up to three times, two seconds apart.
    7. Reply to the senderA threaded reply confirms the route and asks for weight, container quantity, addresses, ship date and Bill of Lading.
    8. Alert the ownerAn email summarises the lead and confirms the deal and the reply are done.
    Error laneIf any step fails, a separate error workflow emails the failed node, the error message and a link to the run.

    From email to deal

    Sample input
    From: Ada OkaforSubject: Quote, 1x40ft used tyres Hamburg to Apapa

    Illustrative example. Names and cargo are invented to show the shape of the data.

    Built to survive bad input

    • Automated senders skipped. Newsletters and no-reply mail never reach the model.
    • Tolerant parsing. Malformed model output creates a flagged lead instead of a lost one.
    • Retries on the CRM. HubSpot calls try three times before the error lane fires.
    • Visible failures. The owner gets the failed node and a run link by email.

    New  Case study · Inventory · WhatsApp agent

    Stockflow

    A WhatsApp assistant that checks and updates stock in Airtable, reads shelf photos and spreadsheets, logs every change, and sends low-stock alerts and a weekly report.

    • n8n
    • Twilio WhatsApp
    • Airtable
    • Groq chat and vision
    • Gmail

    Four ways in

    Chat

    Say what happened

    • Report a sale, restock or removal in plain language
    • The agent finds the item and writes the new total by SKU
    • An audit entry records action, signed change and sender
    • The reply states the new total and flags anything under its reorder level

    Photo

    Snap a shelf or stock sheet

    • A vision model lists the items it can read
    • The list is saved as pending and sent back to check
    • Reply YES and the items are added to inventory
    • Any other reply cancels the import

    File

    Send a CSV or Excel sheet

    • Works from WhatsApp or from a web upload form
    • A model matches your column headers to inventory fields
    • Missing SKUs and units get sensible defaults
    • Items are upserted by SKU and the count comes back

    Scheduled

    Alerts without asking

    • Every day at 8am, items under their reorder level go out by WhatsApp and email
    • Every Monday at 8am, a full stock snapshot plus the last seven days of movements goes out by email

    A short exchange

    Illustrative chat
    sold 3 cargo straps
    Sold 3 Cargo Straps. 9 left. Heads up, that is now below your reorder level of 10.
    added 10 cargo straps
    Added 10. Now 19 in stock.
    Audit log written
    ActionItemChange
    SoldCargo Straps-3
    AddCargo Straps+10

    Guardrails

    • Every change is logged. A write to inventory always comes with an audit entry in the same turn.
    • Sales counted separately. A sale is logged as Sold, other reductions as Remove, so sales total on their own.
    • Photos wait for a YES. A misread photo never touches inventory without confirmation.
    • Re-sending is safe. Items are matched on SKU, so a second upload updates instead of duplicating.
    • Column matching has a backup. If the model cannot map the headers, a fixed list of common names takes over.
    • Valid locations only. Main Store, Apapa Warehouse or Tin Can Warehouse.
    • Plain failures. A file with no readable rows gets a clear reply, and workflow errors go to a separate error workflow.

    How I build

    The boring parts are the job

    Anything works on the happy path. These habits decide whether it still works when a third-party API has a bad morning.

    Idempotent triggers

    The same event arriving twice does not create the record twice. Replays are safe.

    Retry with intent

    Third-party APIs fail. Workflows back off and retry instead of silently dropping the run.

    Duplicate suppression

    Dedupe keys per record and per recipient, so nobody is notified twice about the same thing.

    Logs an operator can read

    Every run writes a timestamped entry, so you can see what fired and what failed without opening the canvas.

    Documented for handover

    Schemas and flow notes help somebody else take the system over without me in the room.

    Self-hosted and maintained

    I run my own n8n on AWS EC2 with Docker, so I own the upgrades and the breakages too.
